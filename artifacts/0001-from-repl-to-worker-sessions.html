From REPL object to worker sessions

The architectural shift in Monty 0.0.19 explains nearly every change required in deepagents-monty.

The old mental model

Before 0.0.19, the middleware constructed a MontyRepl. That object combined four responsibilities: interpreter creation, execution, live REPL state, and serialization.

repl = MontyRepl(limits=..., type_check=...)
result = await repl.feed_run_async(code, ...)
state = repl.dump()

The DeepAgents integration could therefore think, “load one REPL object, run it, dump it.”

The new mental model

In 0.0.19, MontyRepl disappeared. Execution is owned by a pool of crash-isolated worker subprocesses. A checkout dedicates one worker to a session, and the session owns the evolving interpreter state.

AsyncMonty pool Worker subprocess Checked-out session feed_run 
async with AsyncMonty(request_timeout=15) as pool:
    async with pool.checkout(limits={...}) as session:
        await session.load_session(previous_dump)
        result = await session.feed_run(code, ...)
        next_dump = await session.dump()
The key distinction: a pool manages worker capacity and failure isolation; a session manages one stateful Python conversation. LangGraph state stores neither object—it stores an opaque dump between tool calls.

Why this changed our package

1. Persistence became reconstruction

Each python_repl call now checks out a fresh session, loads the prior idle-session dump, executes, and saves a new dump. The visible behavior—variables persist—stays the same, but the mechanism is different.

2. Failure gained a host boundary

max_duration_secs limits interpreter execution. The pool's request_timeout is different: it kills a worker that fails to answer the host. If that happens, the middleware must return a useful error without replacing the last known-good LangGraph snapshot.

3. Host integration protocols moved

External functions are passed as external_lookup, resource limits are checkout configuration, and filesystem callbacks can receive a MontyFileHandle rather than only a path. These sound small, but each touches a different DeepAgents seam.

Maintainer exercise

Without looking back, predict which owner should handle each concern:

  1. How many worker processes may exist?
  2. Whether counter = 41 survives the next tool call?
  3. What happens when a worker stops responding?
  4. Where the opaque state lives between DeepAgents calls?
Reveal answers
  1. The pool.
  2. The session dump and restore cycle.
  3. The pool's request timeout and crash handling.
  4. LangGraph state, Base64-encoding the dump for serialization.

The maintenance habit to keep

For every future Monty release, inspect five seams: lifecycle, persisted state, host callbacks, resource/error boundaries, and model-visible capabilities. The 0.0.19 maintainer map turns those seams into a regression checklist.

Primary reading: the tagged Monty 0.0.19 Python API guide. Focus on “Basic execution,” “Snapshots,” “Resource limits,” and “Crash isolation.”
